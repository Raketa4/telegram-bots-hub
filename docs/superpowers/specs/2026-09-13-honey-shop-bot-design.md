# honey-shop-bot: дизайн

Дата: 2026-09-13

## Цель

Telegram-бот — тестовый магазин по продаже мёда с оплатой в Telegram Stars
(XTR). Пользователь явно видит с первого сообщения, что магазин тестовый и
реальный товар не отправляется. После оплаты бот собирает данные для
(символической) доставки через пункт выдачи Ozon.

Живёт в `telegram-bots-hub/bots/honey-shop/` — подпапка общего репозитория
сайта-хаба (`telegram-bots-hub`), но написана независимо от него (чистый
Python stdlib, конфиг через `.env`, никаких абсолютных/Windows-путей внутри
`bot.py`), чтобы позже перенести на VPS простым копированием папки.

## Архитектура

Повторяет проверенный паттерн бота `@peneksel_bot` (проект «Поцык»):
чистая стандартная библиотека Python, long polling через `urllib`/
`http.client`, без сторонних пакетов и venv.

```
telegram-bots-hub/
  bots/
    honey-shop/
      bot.py              # главный цикл: long polling, роутинг апдейтов
      catalog.py           # список товаров
      state.py             # in-memory корзины и состояния оформления заказа
      .env.example
      .env                 # реальный токен, в .gitignore
      orders.jsonl          # лог заказов, в .gitignore (персональные данные)
      bot.log               # в .gitignore
      autostart-install.ps1
      autostart-uninstall.ps1
      README.md
      tests/
        test_state.py       # офлайн-тесты без сети
```

## Каталог товаров (`catalog.py`)

Фиксированный список, правится вручную:

| id | Название      | Цена, Stars |
|----|---------------|-------------|
| 1  | Липовый       | 60          |
| 2  | Гречишный     | 70          |
| 3  | Цветочный     | 55          |
| 4  | Разнотравье   | 65          |

## Данные и состояние (только в памяти процесса, без БД)

- `CATALOG: list[Product]` — статический список выше.
- `carts: dict[user_id, dict[product_id, qty]]` — текущая корзина
  пользователя. Пустая/отсутствующая запись = пустая корзина.
- `checkout_state: dict[user_id, CheckoutState]`, где `CheckoutState` —
  одно из: `NONE`, `AWAITING_ADDRESS`, `AWAITING_PHONE`, плюс накопленные
  на этом шаге данные заказа (снимок корзины на момент оплаты, сумма,
  адрес после его ввода).

Всё состояние живёт в памяти процесса и теряется при перезапуске — для
тестового магазина это приемлемо (в рамках, см. ниже).

## Пользовательский флоу

1. `/start` → приветствие, содержащее явным текстом:
   **"⚠️ Это тестовый магазин. Реальный товар не отправляется."**
   Плюс краткое описание и инлайн-кнопка «🛍 Каталог».
2. «Каталог» → сообщение с инлайн-кнопками на каждый сорт мёда
   (`callback_data = "add:<product_id>"`), при нажатии — товар добавляется
   в корзину (или увеличивается qty), бот подтверждает всплывающим
   `answerCallbackQuery`. Отдельная кнопка «🧺 Корзина (N, M Stars)»
   с живым счётчиком.
3. «Корзина» → список позиций с количеством и кнопками `-`/`+` на каждую
   (`callback_data = "dec:<id>"` / `"inc:<id>"`), кнопка «Оформить заказ»
   (неактивна/не показывается, если корзина пуста) и «Очистить корзину».
4. «Оформить заказ» → `sendInvoice`, валюта `XTR`, `prices` — по одной
   позиции на товар (`label = "<Название> × <qty>"`, `amount = price*qty`),
   `payload` содержит слепок корзины для сверки на `pre_checkout_query`.
5. `pre_checkout_query` → `answerPreCheckoutQuery(ok=True)`, если корзина
   пользователя всё ещё непуста и совпадает по сумме с `payload`; иначе
   `ok=False` с сообщением об ошибке.

   **Отклонение от спеки (намеренное):** в реализации сверка идёт только
   против самого `payload` инвойса (`total_for_items(items) ==
   total_amount` и валюта `XTR`), а не против текущей живой корзины
   пользователя. `payload` — это авторитетный снимок того, на что
   пользователь согласился заплатить в момент выставления счёта; сверка
   с живой изменяемой корзиной ошибочно отклоняла бы легитимные оплаты
   от пользователя, который продолжил менять корзину после выставления
   инвойса, но до оплаты. Это сознательное улучшение по сравнению с
   исходной формулировкой спеки — не "чинить обратно" по этому тексту.
6. `successful_payment` → корзина очищается, `checkout_state[user_id]`
   переводится в `AWAITING_ADDRESS` с сохранением состава и суммы заказа.
   Бот отправляет: "Оплата прошла (⭐ N Stars)! Так как магазин тестовый,
   но давайте разыграем доставку по-настоящему — пришлите адрес пункта
   выдачи Ozon."
7. Текстовое сообщение при `AWAITING_ADDRESS` → сохраняется как адрес,
   состояние → `AWAITING_PHONE`, бот просит номер телефона, привязанный к
   аккаунту Ozon.
8. Текстовое сообщение при `AWAITING_PHONE` → сохраняется как телефон,
   заказ целиком (user_id, username, состав, сумма, адрес, телефон,
   timestamp) дописывается одной JSON-строкой в `orders.jsonl`,
   `checkout_state[user_id]` → `NONE`. Бот присылает итоговое
   подтверждение с деталями заказа и повторной пометкой, что это тест.
9. Текстовое сообщение при `checkout_state == NONE` (не относится к
   оформлению) → игнорируется ботом либо получает подсказку
   "Наберите /start, чтобы открыть каталог" (не мешает пользователю
   писать что угодно вне флоу оформления).

## Команды

- `/start` — приветствие + пометка «тест» (см. выше).
- `/help` — краткая справка по кнопкам.
- `/paysupport` — обязательная команда Telegram при приёме платежей;
  для теста — заглушка с контактом пользователя-владельца бота.

## Возвраты (refund)

Как в `@peneksel_bot`: вручную, вызовом `refundStarPayment` при
необходимости. Отдельной команды в боте нет — вне рамок.

## Устойчивость к ошибкам

- Главный цикл оборачивает обработку каждого апдейта в try/except и не
  падает на непредвиденных ошибках Bot API (тот же паттерн, что в
  `Поцык/bot/bot.py`), тихо переживает `409 Conflict` от параллельного
  поллера.
- `pre_checkout_query` всегда явно отвечает (ok или отказ) — Telegram
  отменяет платёж, если ответа нет вовремя.
- Ввод "мусора" на шаге адреса/телефона принимается как есть (это
  тестовый магазин, форматной валидации телефона/адреса нет) — не
  входит в рамки.

## Логирование и хранение данных

- `bot.log` — технический лог (консоль + файл, ротация при 1 МБ, как в
  Поцыке).
- `orders.jsonl` — одна JSON-строка на завершённый заказ. Содержит
  персональные данные (адрес, телефон) → в `.gitignore`, не коммитится.
- Токен — в `.env` (`TELEGRAM_BOT_TOKEN=...`), не коммитится; в репозитории
  только `.env.example` с плейсхолдером.

## Деплой и автозапуск

Задача Планировщика заданий Windows `HoneyShopBot`:
`pyw.exe -3.14 bot.py`, триггер «при входе пользователя», рестарт 1/мин
при сбое, один экземпляр (`IgnoreNew`), без лимита времени — копия
паттерна `PotsykBot` (`bot/autostart-install.ps1` в проекте Potsyk),
адаптированная под новый путь и имя задачи.

Перенос на VPS в будущем: скопировать `bots/honey-shop/` + `.env`,
заменить автозапуск на systemd-юнит/screen — код `bot.py` менять не
требуется, т.к. он не содержит ничего специфичного для Windows кроме
самих `.ps1`-скриптов автозапуска.

## Хаб (telegram-bots-hub/js/bots.js)

Отдельным шагом после того, как бот создан и известен `username`: одна
запись из `BOTS` (например `id: 1`) получает
`username: "<созданный_бот>"`, `title` меняется на что-то вроде
«Магазин мёда (тест)». Правка одной строки в `js/bots.js`, без изменений
HTML/CSS — существующий рендер (`js/render.js`, `js/main.js`) уже это
поддерживает.

## Тестирование

- Юнит-тесты (`tests/test_state.py`, запуск `node`-стиль на чистом
  `python -m unittest`/`pytest` не нужен — используем `unittest` из
  stdlib) на чистые функции без сети:
  - расчёт суммы и состава корзины;
  - переходы `checkout_state` (`NONE → AWAITING_ADDRESS → AWAITING_PHONE
    → NONE`);
  - формирование `prices` для `sendInvoice` из корзины;
  - парсинг `callback_data` (`add:`, `inc:`, `dec:`).
- Офлайн-тест `handle_update` с моком `api` (как для Поцыка) — прогон
  всех веток: `/start`, каталог, корзина, инвойс, `pre_checkout_query`,
  `successful_payment`, адрес, телефон.
- Ручная проверка: реальный запуск с long polling, полный путь в живом
  Telegram-клиенте `/start → каталог → корзина → оформить заказ →
  инвойс` (без реальной оплаты Stars — только проверка, что инвойс
  доходит и параметры валидны против Bot API, как это делали для
  Поцыка), затем ручная имитация `successful_payment` не проводится (это
  требует реальной оплаты) — эта ветка проверяется только через
  офлайн-мок.

## Вне рамок

- База данных, персистентность состояния между перезапусками процесса.
- Валидация формата адреса/телефона.
- Реальная интеграция с Ozon (это тестовый магазин, доставка не
  выполняется по-настоящему).
- Отдельная команда возврата Stars внутри бота.
- Многоязычность, мультивалютность.
